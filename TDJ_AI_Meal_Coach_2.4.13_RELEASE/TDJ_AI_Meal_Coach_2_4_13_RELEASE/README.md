# TDJ AI 餐盤教練 2.4.13 RELEASE

## 本版重點：真正背景工作佇列
- Web Service 收到餐點後，只負責壓縮照片並將工作寫入既有 PostgreSQL。
- `worker.py` 由 Render Background Worker 執行 AI 分析。
- 學員送出後立即看到「餐點已收到」，可以離開頁面，稍後回「查看最近紀錄」。
- 最近紀錄會顯示「排隊中 / 分析中 / 分析失敗」，有待處理工作時每 8 秒更新。
- 分析失敗不會永遠卡在分析中，並允許重新送出。
- 不需要 Redis / Key Value；直接使用既有 PostgreSQL 做 durable queue。

## Render 部署
### Web Service
Root Directory: `TDJ_AI_Meal_Coach_2_4_13_RELEASE`
Start Command: `gunicorn app:app --timeout 120`（或沿用目前設定）

### 新增 Background Worker
使用同一個 GitHub repository / branch。
Root Directory: `TDJ_AI_Meal_Coach_2_4_13_RELEASE`
Start Command: `python worker.py`
Environment 必須至少複製 Web Service 的：`DATABASE_URL`、`OPENAI_API_KEY`，以及 AI 分析實際使用到的相同環境變數。

> 重要：部署 2.4.13 Web Service 後，必須同時建立並啟動 Background Worker，否則工作會停在「排隊中」。

## 2.4.6 脂肪判斷優化
- 單餐脂肪較高不再直接等同於「吃得太油」。
- AI 區分食物本身脂肪、烹調油脂、混合與無法確定。
- 鯖魚、鮭魚、蛋、堅果等食材脂肪不再自動被描述為烹調過油。
- 只有炸物、麻油、三杯、明顯油煎/大量炒油或濃厚油醬等有足夠證據時，才提示烹調油脂。
- 全天脂肪累積判斷維持原有每日目標邏輯。

## 2.4.11｜512MB 記憶體優化
- 上傳照片逐張處理，不再先把所有原始手機照片完整讀進 RAM。
- 照片自動校正方向、長邊縮至最多 2048px、JPEG 品質 82，保留餐點與營養標示人工檢視可讀性。
- 多圖獨立預讀最多同時 2 張，避免 3–5 張照片同時 Base64/API 請求造成 RAM 尖峰。
- 前台／後台歷史照片改為逐張 lazy-load，不再一次把 7／14／21／30 天所有 Base64 圖片載入 Python 記憶體。
- 單次 multipart 上傳上限預設 40MB；單張無法壓縮的原始格式上限 15MB。
- 不變更 PostgreSQL schema，不清除既有會員、餐點、飲水、照片、顧問或方案資料。

## 2.4.12｜記憶體生命週期保護
- 保留 2.4.10 圖片縮圖/lazy-load 與 2.4.11 AI 排隊保護。
- 每次 AI 分析結束後主動關閉 OpenAI/httpx client connection pool，移除大型 Base64/API payload 參照並執行 GC。
- 儲存餐點照片時逐張釋放暫存 Base64 字串。
- 新增 Render Logs 的 `MEMORY stage=... rss_mb=...` 診斷紀錄，可判斷 RAM 是單次尖峰還是逐次累積。
- Gunicorn 固定 1 worker / 2 threads，避免多 worker 複製 Python/Pillow 記憶體；每 20–25 個 request 自動平滑 recycle worker，將 allocator 保留的 RSS 真正還給作業系統。
- 不變更 PostgreSQL schema，不清除既有資料。
